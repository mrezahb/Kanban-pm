# برنامهٔ اجرای پروژه

این برنامه نقشهٔ اجرایی MVP است. موارد هر مرحله را پس از تکمیل علامت بزن؛ اگر بررسی یا آزمونی شکست خورد، علت را با شواهد پیدا کن و پیش از ادامه برطرفش کن. مستندات برنامه‌ریزی و اجرا در `docs/` قرار می‌گیرند؛ راهنمای عامل هر بخش، مانند `frontend/AGENTS.md` و `backend/AGENTS.md`، کنار کد همان بخش قرار می‌گیرد.

## تصمیم‌های تثبیت‌شده و معیارهای سراسری

- فرانت‌اند: Next.js با خروجی ایستا؛ بک‌اند: FastAPI؛ پایگاه داده: SQLite محلی.
- کل برنامه در یک کانتینر Docker اجرا می‌شود. FastAPI فایل‌های ایستای Next.js را از `/` ارائه می‌کند.
- ورود MVP با نام کاربری `user` و گذرواژهٔ `password` است. مدل داده باید چند کاربر را پشتیبانی کند؛ در MVP هر کاربر فقط یک برد دارد.
- نشست ورود ۷ روز اعتبار دارد و خروج باید نشست را باطل کند.
- مدل OpenRouter برابر `openai/gpt-oss-120b` است. کلید فقط از `OPENROUTER_API_KEY` در `.env` ریشه خوانده شود و هرگز در کد، خروجی رابط یا گزارش‌ها افشا نشود.
- دستیار می‌تواند کارت ایجاد، ویرایش یا جابه‌جا کند و تغییر معتبر را بدون تأیید جداگانه اعمال می‌کند. پاسخ و نتیجهٔ تغییر باید به کاربر نمایش داده شود.
- رابط باید خوانا باشد و جابه‌جایی کارت‌ها موشن محسوس و روان داشته باشد؛ با `prefers-reduced-motion` حرکت کاهش یابد.
- حداقل پوشش خطوط اجرایی آزمون‌ها: ۸۰٪ برای فرانت‌اند و جداگانه ۸۰٪ برای بک‌اند.
- درخواست‌های تغییردهنده، از جمله درخواست‌های دستیار، باید سمت سرور اعتبارسنجی و در SQLite پایدار شوند.
- بازبینی و تأیید کاربر برای طرح پایگاه داده و نسخهٔ قابل‌استفادهٔ نهایی، در نقاط مشخص زیر الزامی است.

## مرحلهٔ ۱: بررسی و آماده‌سازی

### کارها

- [ ] `AGENTS.md` و این برنامه را پیش از شروع پیاده‌سازی بخوان.
- [ ] ساختار و رفتار فرانت‌اند موجود را بررسی کن و نقاطی را که به API، ورود یا خروجی ایستا وابسته‌اند مشخص کن.
- [ ] راهنمای `frontend/AGENTS.md` را با توضیح ساختار، اجرای برنامه، آزمون‌ها و قراردادهای رابط ایجاد کن.
- [ ] راهنمای `backend/AGENTS.md` را با مسئولیت‌ها، ساختار، تنظیمات، API، پایگاه داده و آزمون‌های بک‌اند تکمیل کن.
- [ ] پیش‌نیازها و دستورات لازم برای ساخت، آزمون و اجرای محلی را در مستندات مرتبط ثبت کن.

### آزمون‌ها و معیار تکمیل

- [ ] راهنمای هر بخش با ساختار واقعی همان بخش تطبیق دارد و به‌تنهایی برای یافتن کد و آزمون‌های آن کافی است.
- [ ] فایل‌های تنظیمات و آزمون موجود بررسی شده‌اند و برنامهٔ مراحل بعدی با آن‌ها تعارض ندارد.

## مرحلهٔ ۲: زیرساخت اجرا و Docker

### کارها

- [ ] Dockerfile و تنظیمات لازم را طوری بساز که فرانت‌اند ابتدا به‌شکل ایستا ساخته و سپس توسط FastAPI ارائه شود.
- [ ] FastAPI را در `backend/` ایجاد کن و یک مسیر سلامت ساده برای بررسی آماده‌به‌کار بودن سرویس اضافه کن.
- [ ] فایل SQLite را در مسیر پایدار و قابل‌نگاشت به volume قرار بده تا با توقف یا بازسازی کانتینر از بین نرود.
- [ ] اسکریپت‌های راه‌اندازی و توقف کانتینر را برای macOS، Windows و Linux در `scripts/` فراهم کن.
- [ ] تنظیمات لازم را از محیط دریافت کن؛ `.env` ریشه را وارد مخزن یا تصویر نکن.

### آزمون‌ها و معیار تکمیل

- [ ] با یک کانتینر، مسیر `/` یک صفحهٔ HTML ایستا را ارائه می‌کند و مسیر سلامت API پاسخ موفق می‌دهد.
- [ ] سرویس با اسکریپت‌های راه‌اندازی قابل اجرا و با اسکریپت‌های توقف قابل متوقف‌کردن است.
- [ ] فایل پایگاه داده و تنظیمات با توقف کانتینر حذف یا افشا نمی‌شوند.

## مرحلهٔ ۳: فرانت‌اند ایستا و برد نمایشی

### کارها

- [ ] فرانت‌اند موجود را برای build ایستا و ارائه از FastAPI آماده کن؛ رفتارها و ظاهر اصلی نمونه را حفظ کن.
- [ ] برد نمایشی را با ستون‌های ثابت و قابل‌تغییرنام و کارت‌های قابل‌ویرایش نمایش بده.
- [ ] کشیدن و رها کردن کارت‌ها را با بازخورد حرکتی روان پیاده‌سازی کن.
- [ ] حالت‌های بارگذاری، خطا و صفحه‌نمایش‌های مختلف را بررسی کن؛ رعایت `prefers-reduced-motion` را اضافه کن.

### آزمون‌ها و معیار تکمیل

- [ ] build ایستای Next.js موفق است و صفحهٔ برد از `/` بارگذاری می‌شود.
- [ ] آزمون‌های واحد، رندر برد، ویرایش کارت و ستون و جابه‌جایی کارت را پوشش می‌دهند.
- [ ] آزمون مرورگر، جابه‌جایی کارت با کشیدن و رها کردن و کاهش حرکت را بررسی می‌کند.

## مرحلهٔ ۴: طراحی و تأیید پایگاه داده

### کارها

- [ ] مدل داده‌ای برای کاربران، برد، ستون‌ها، کارت‌ها و نشست‌های ورود طراحی کن.
- [ ] یکتایی نام کاربری، ارتباط رکوردها با مالک، ترتیب ستون‌ها و کارت‌ها و یک‌برد-برای-هر-کاربر را مشخص کن.
- [ ] طرح را در `docs/database-schema.json` ذخیره و منطق تصمیم‌ها را در `docs/` مستند کن.
- [ ] طرح و فرض‌های مهم را برای بازبینی و تأیید کاربر ارائه کن؛ پیش از تأیید، مبنای پیاده‌سازی را نهایی نکن.

### آزمون‌ها و معیار تکمیل

- [ ] طرح JSON معتبر است و همهٔ نیازهای چندکاربره و محدودیت یک برد برای هر کاربر را پوشش می‌دهد.
- [ ] تأیید کاربر برای طرح ثبت شده است.

## مرحلهٔ ۵: بک‌اند، ورود و API برد

### کارها

- [ ] اتصال SQLite و ایجاد خودکار پایگاه داده و ساختار لازم در اولین اجرا را پیاده‌سازی کن.
- [ ] ورود با `user` و `password`، نشست ۷روزه و خروجی که نشست را باطل می‌کند اضافه کن.
- [ ] دسترسی به API برد را به نشست معتبر محدود کن؛ اطلاعات کاربر دیگری نباید از API قابل‌خواندن یا تغییر باشد.
- [ ] APIهای لازم برای خواندن و به‌روزرسانی برد، ستون‌ها و کارت‌ها را پیاده‌سازی کن.
- [ ] ورودی‌ها و تغییرهای برد را سمت سرور اعتبارسنجی کن و خطاهای ناموفق را با پاسخ روشن گزارش بده.

### آزمون‌ها و معیار تکمیل

- [ ] آزمون واحد بک‌اند ورود موفق/ناموفق، انقضای نشست، خروج، مالکیت داده‌ها و عملیات برد را پوشش می‌دهد.
- [ ] در اجرای تازه، پایگاه داده خودکار ساخته می‌شود و عملیات CRUD پس از راه‌اندازی مجدد باقی می‌ماند.
- [ ] درخواست بدون نشست معتبر نمی‌تواند برد را بخواند یا تغییر دهد.

## مرحلهٔ ۶: اتصال فرانت‌اند به بک‌اند

### کارها

- [ ] ورود و خروج رابط را به API متصل کن و برد را فقط پس از ورود نمایش بده.
- [ ] بارگذاری، ذخیره و تغییر کارت‌ها و نام ستون‌ها را از API انجام بده.
- [ ] پس از تغییر موفق، وضعیت رابط را با دادهٔ پایدار سرور هماهنگ کن؛ خطاها را بی‌صدا نادیده نگیر.
- [ ] راه‌اندازی اولیه را به‌گونه‌ای انجام بده که پایگاه دادهٔ جدید به برد قابل‌استفاده منجر شود.

### آزمون‌ها و معیار تکمیل

- [ ] آزمون یکپارچه، ورود، دریافت برد، ایجاد/ویرایش/جابجایی کارت، خروج و منع دسترسی پس از خروج را پوشش می‌دهد.
- [ ] تغییر برد پس از بارگذاری مجدد صفحه و راه‌اندازی دوبارهٔ کانتینر باقی می‌ماند.
- [ ] کاربر واردنشده برد را نمی‌بیند و کاربر واردشده فقط به برد خودش دسترسی دارد.

## مرحلهٔ ۷: اتصال بک‌اند به OpenRouter

### کارها

- [ ] کلید `OPENROUTER_API_KEY` و مدل `openai/gpt-oss-120b` را در درخواست بک‌اند استفاده کن.
- [ ] خطاهای نبود کلید، خطای شبکه و پاسخ نامعتبر سرویس را به‌صورت روشن مدیریت کن.
- [ ] آزمون اتصال محدود با پرسش `2+2` را بدون افشای کلید یا اتکا به پاسخ ثابت اجرا کن.

### آزمون‌ها و معیار تکمیل

- [ ] آزمون واحد با پاسخ سرویس شبیه‌سازی‌شده، ساخت درخواست صحیح و مدیریت خطاها را بررسی می‌کند.
- [ ] آزمون اتصال واقعی فقط در صورت تنظیم کلید اجرا می‌شود و پاسخ دریافتی قابل‌مشاهده است.
- [ ] کلید در کد منبع، لاگ‌ها، پاسخ API یا خروجی مرورگر ظاهر نمی‌شود.

## مرحلهٔ ۸: گفت‌وگوی ساختاریافته و اعمال تغییرهای دستیار

### کارها

- [ ] درخواست مدل شامل برد کامل به‌صورت JSON، پرسش جاری کاربر و تاریخچهٔ مکالمه باشد.
- [ ] خروجی ساختاریافته را برای پاسخ متنی و تغییر اختیاری برد تعریف و در بک‌اند اعتبارسنجی کن.
- [ ] تغییرهای مجاز را به ایجاد، ویرایش و جابه‌جایی کارت محدود کن؛ تغییر معتبر را بدون تأیید جداگانه اعمال کن.
- [ ] تغییر را از مسیر اعتبارسنجی و ذخیره‌سازی سرور اجرا کن؛ در صورت شکست، آن را به‌عنوان موفقیت گزارش نکن.
- [ ] تاریخچه و داده‌های برد را فقط در محدودهٔ کاربر واردشده پردازش کن.

### آزمون‌ها و معیار تکمیل

- [ ] آزمون‌های واحد برای پاسخ فقط متنی، هر نوع تغییر، خروجی نامعتبر و خطای ذخیره‌سازی وجود دارد.
- [ ] آزمون یکپارچه تأیید می‌کند تغییر معتبر فوراً در پایگاه داده ذخیره شده و دادهٔ برد را ناخواسته از بین نمی‌برد.
- [ ] پاسخ مدل نامعتبر یا ناموفق باعث تغییر برد نمی‌شود و خطای قابل‌فهم به کاربر می‌رسد.

## مرحلهٔ ۹: رابط دستیار هوش مصنوعی

### کارها

- [ ] ابزارک گفت‌وگو را در Sidebar با ارسال پیام و نمایش تاریخچه بساز.
- [ ] وضعیت‌های درحال‌ارسال، پاسخ متنی، اعمال تغییر و خطا را واضح نمایش بده.
- [ ] بعد از تغییر موفق توسط دستیار، برد را از بک‌اند تازه‌سازی کن.
- [ ] خوانایی، رنگ‌های تعریف‌شده، دسترس‌پذیری پایه و موشن کارت‌ها را در رابط نهایی رعایت کن.

### آزمون‌ها و معیار تکمیل

- [ ] آزمون فرانت‌اند ارسال پیام، نمایش پاسخ، تازه‌سازی برد پس از تغییر و نمایش خطا را پوشش می‌دهد.
- [ ] آزمون مرورگر یک گفت‌وگو را تا مشاهدهٔ تغییر ذخیره‌شده روی برد طی می‌کند.
- [ ] تغییر کارت با موشن روان انجام می‌شود و در حالت کاهش حرکت، حرکت اضافه حذف یا کاهش می‌یابد.

## مرحلهٔ ۱۰: اعتبارسنجی نهایی و پذیرش

### کارها

- [ ] آزمون‌های واحد، یکپارچه‌سازی و مرورگر را اجرا کن و خطاهای مرتبط را برطرف کن.
- [ ] گزارش پوشش را برای هر دو بخش جداگانه تولید کن و حداقل ۸۰٪ پوشش خطوط اجرایی را تأیید کن.
- [ ] اجرای نصب/راه‌اندازی، ورود، کار با برد، گفت‌وگو، توقف و راه‌اندازی مجدد را در Docker بررسی کن.
- [ ] مستندات و راهنماهای عامل را با پیاده‌سازی نهایی هماهنگ کن.
- [ ] نسخهٔ اجراشدنی را برای بررسی کاربر ارائه کن و تأیید نهایی را بگیر.

### معیار پذیرش نهایی

- [ ] برنامه در یک کانتینر Docker اجرا می‌شود و FastAPI فرانت‌اند ایستا را از `/` ارائه می‌کند.
- [ ] ورود با اطلاعات MVP، نشست ۷روزه و خروج کار می‌کند.
- [ ] برد و تغییرهای آن در SQLite پایدار می‌مانند.
- [ ] دستیار با OpenRouter گفت‌وگو می‌کند و تغییر معتبر کارت‌ها را خودکار ذخیره و در رابط نمایش می‌دهد.
- [ ] آزمون‌های لازم موفق‌اند، پوشش خطوط هر دو بخش حداقل ۸۰٪ است و کاربر نسخه را تأیید کرده است.
